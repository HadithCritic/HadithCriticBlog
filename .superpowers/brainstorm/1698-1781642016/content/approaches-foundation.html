Foundation for the Core Vault: three options

Research-backed and license-verified. Two hard requirements decide it: (1) markdown files are the source of truth (the Obsidian model, where plugins manipulate text), and (2) a safe, first-class plugin + theme ecosystem. Pick in the terminal.

1 — Greenfield: Tauri 2 + CodeMirror 6  ★ recommended

Reuse your data assets; SilverBullet + the atomic-editor repo as Live-Preview references; Obsidian's plugin API as a shape to follow.
Build the CM6 source-first editor + Live Preview, the Tauri vault/file layer, search, and the plugin host.

Pros

  • Source-first markdown + best native Arabic/RTL (CM6 bidi)
  • CM6 facets map almost 1:1 onto a plugin API
  • Tauri has no Node in the webview, the only realistic safe plugin model
  • Tiny, fast binary; matches the PRD; you own the architecture

Cons

  • Most engineering of the three
  • Rust + Tauri toolchain on Windows (MSVC + WebView2)
  • You build Live Preview and the plugin host yourself
  • Cross-platform WebView QA deferred (Win-first hides it)
2 — Fork Cabinet (MIT)

Reuse file-watch + SQLite index, search, theme system, RTL/i18n groundwork, lots of scaffolding.
Build a real plugin API (it has none) and fight the editor paradigm.

Pros

  • Biggest head start; MIT; actively developed
  • Closest overall "vibe"; RTL already moving

Cons

  • TipTap/ProseMirror is rich-text, NOT source-first (markdown becomes lossy import/export, wrong model for text-manipulating plugins)
  • No plugin ecosystem anyway (AI "skills" + HTML embeds only)
  • Young, solo-maintained, pre-1.0, likely to churn under you
  • Next.js + Electron, heavier; AI-centric design you may not want
3 — Build on SilverBullet (MIT, CM6)

Reuse CM6 source-first editor + RTL; clean codebase; Lua in-app extensibility.
Build a desktop shell + offline packaging (it is a self-hosted web app); rework the Lua model toward your plugin story.

Pros

  • Right editor already (CM6, source-first, good RTL)
  • MIT; more mature and cleaner than Cabinet

Cons

  • Not a desktop app; you add the shell and offline packaging
  • Lua plug paradigm is non-standard (no Obsidian mental model reuse)
  • Deno backend; you would be bending someone else's app

My recommendation

Go greenfield (option 1). The two things that define your product, source-first markdown and a safe plugin ecosystem, are exactly what Tauri + CM6 nails and what the forks fight. Use SilverBullet and atomic-editor as references to port from, not bases to inherit. Honest caveat: it is the most work and carries a Rust/Tauri learning curve. If "usable as soon as possible" outweighs "right architecture for the ecosystem," forking Cabinet is the pragmatic alternative, but expect to retrofit the editor and plugin model later.
